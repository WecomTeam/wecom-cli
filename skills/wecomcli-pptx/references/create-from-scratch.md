# 从零构建PPT的教程

## 制定任务计划

> **任务命名约束（强约束）**：本表仅为内部执行参考。在创建 TODO / 任务（TaskCreate）或向用户汇报进度时，**必须使用面向用户的术语**（如「内容大纲 / 风格设计 / 创建演示文稿 / 逐页制作 / 检查页面 / 交付」），**禁止暴露任何内部实现字眼**（如 `JSX`、`DSL`、`*.jsx`、`docid`、`wecom-cli slide ...` 命令名、`is_success`、源码、组件文件名等）。**失败 / 排查 / 重试的对外话术同样受限**：只说「制作中 / 遇到问题正在重试 / 换个方式重新生成」，不贴错误码、不描述内部通道与排查过程、不引用技能规则原文。

| Step | 职责（内部）                                   | 产物（内部）                                 |
| ---- | ---------------------------------------------- | -------------------------------------------- |
| 1    | 信息收集（每次判定，命中信号时必做）           | `RESEARCH.md`（判定结论 + 来源清单）         |
| 2    | 需求对齐（轻量确认 + 风格预览卡，必弹）        | 关键信息已确认 + 风格参数已锁定              |
| 3    | 依据主题+信息构建PPT的叙述逻辑                 | `STORY.md`                                   |
| 4    | 构建页面风格的设计逻辑                         | `DESIGN.md`                                  |
| 5    | 创建在线演示文稿并持久化设计契约               | `docid` 已拿到 + 设计契约已写入（写操作解锁）|
| 6    | 配图准备（材料图过上传口，无图位定版式替代）   | 全部图位已拿到上传口的 URL 或确定替代方案   |
| 7    | 逐页生成并插入（`page_index` 递增）            | 全部页面已在线成型                           |
| 8    | 核对结构                                       | 页数与顺序与大纲一致                         |
| 9    | 交付                                           | 在线文档链接已给到用户 |


## 各步骤要求
### Step1：信息收集（每次判定，命中信号时必做）
当模型的信息不足、数据过时或需要行业标杆案例时，主动调用网络搜索的工具进行信息的收集，挖掘有深度、有据可查的实时内容。
判断信号：
- 主题涉及 `数字 / 市场 / 行业 / 新闻 / 政策 / 竞品 / 分析` 等具有时效性的信息时 → 需要最新统计数据。
- 主题含`陌生缩写 / 专业术语 / 生僻词组 / 具体的公司、产品、人物、事件` → 先查清楚。
- 用户明确要求 或 用户需要"有说服力"但未提供素材 → 补充外部佐证。
- 打算在页面上写用户没给的具体数字、年份、排名、引语 → 必须有出处。

用户 PPT 模板里的文字与数字（占位句、说明文字、示例营收 / 增长率 / 人数等）**不是来源**，不写进 `RESEARCH.md`，也不能拿来支撑页面上的数字（create-from-template.md §T2）。

本步必须留下本地 `RESEARCH.md`：第一行写判定（`调研：需要（命中：…）` 或 `调研：不需要（理由：…）`；「不需要」只在用户已给完整材料、纯内部主题且事实齐全、用户明说不联网、用户只要版式示例时成立），其后每条一行「事实 · 来源 · 时间 · 链接」。搜索不可用就如实写明并告知用户，不得编造来源。Step3 写大纲时每个具体数字都要能在 `RESEARCH.md` 或用户材料里找到，找不到的删掉或标「示例数据」；交付时一句话说明调研情况。

### Step2：需求对齐
按 [human-alignment.md](human-alignment.md) 执行。要点：
- 🔴 **本步永远不阻塞 Step3**：提问卡与预览卡发出后拿不到回应（没点 / 审批超时 / 组件失败）→ 按 human-alignment §1「无回应兜底」取默认值，**直接进 Step3 把 PPT 做完**，不重发、不追问、不中止、不交空结果
- 交付形态固定为在线文档链接，不问用户
- 能推断就推断，文字提问 ≤ 3 个
- **选套前置**：出预览卡之前先按 Step4「选套」在全池打分取前 3 套（政务闸门命中则取政务两套），预览卡的构成、配色与跳过规则见 [templates/README.md](templates/README.md) §2；Step4 沿用本步的候选与选定的套，不再重判
- 进入 Step3 前必须已选定一套范例（用户在预览卡选定，或按 README §2 的跳过规则选定）；**用户上传了自己的 PPT 模板时不选范例套**，按 [create-from-template.md](create-from-template.md) 从模板生成外壳，本文件 Step2 的预览卡、Step4 的选套与配色、Step7 的 `init` 与 `ref_*.slide` 都不适用，其余步骤照常；只有该文件 T1.6 末尾那一种情况（模板读不出版式、渲染图也拿不到）才回到本文件的范例池流程，且配色按模板主色的色相推、交付时说明版式是同风格重排；配色不是该套默认时，DESIGN.md 记映射表并按 README §3 换色
- 对齐结果中的主题/目标 → 作为 Step3 构建叙事的输入
- 对齐结果中的风格参数（色板/字体/密度基线）→ 作为 Step4 设计阶段的硬约束

### Step3：构建叙事逻辑 （STORY.md）
动笔前先读回 `RESEARCH.md`（不存在就回 Step1 补判定）。
阅读 [story-principle.md](story-principle.md)，最后生成一个STORY.md的文件。

### Step4：构建页面风格的逻辑 (DESIGN.md)

#### 选套（本流程在 Step2 出预览卡之前执行一次，Step4 沿用其结论）

> 用户上传了自己的 PPT 模板：本节不执行，`DESIGN.md` 以 `template` 生成的 `DESIGN.template.md` 为主体（create-from-template.md T3）。

范例池是**扁平的 9 套**，没有分支。选套 = 在全池上打一次分，取前 3 套作预览卡候选。只读 `assets/templates/index.json`，不要逐套翻预设。

**第一步：政务闸门（唯一的硬分区）**

先看 `index.json` 的 `gate.trigger_zh` 是否命中——主体是党政机关、事业单位、国企央企、街道社区、学校党组织、群团组织；或场景是工作报告、述职述廉、党课、主题教育、宣讲、政策解读、督查巡察、表彰大会、周年纪念、红色文化；或文风是公文体（「一是、二是」「进一步」「切实」）。

- **命中** → 候选**只在 `gate.sets`（政务工作 / 表彰庆典）里取**，预览卡只出 2 张，并额外加载 [government-contract.md](government-contract.md)。不进下面的打分。
- **未命中** → 全池 9 套都是候选，往下打分。

**第二步：三项打分，取前 3**

| 项 | 怎么算 | 权重 |
| :-- | :-- | :-- |
| 场景贴合 | 用户场景与该套 `scenes_zh` / `best_for_zh` 的贴合度；命中 `avoid_for_zh` 直接出局 | 最高 |
| 正式度贴近 | 先给本次定一档正式度，再取 `tags.formality_rank` 差值最小的；差 ≥2 档的不进前 3 | 次之 |
| 差异 | 选出的 3 套，`tags.tone` 与 `tags.density` **不得全同**；全同就把第 3 名换成最近的异类 | 兜底 |

本次正式度怎么定——问一句「给谁看、说错了要紧吗」：

| 档位 | 什么场合 | 对应 formality |
| :-- | :-- | :-- |
| 刚性 | 出错是事故：合规、审计、董事会、投资人、对外正式发布 | 高 / 中高 |
| 常规职场 | 日常汇报、提案、复盘、评审、经营分析 | 中高 / 中 |
| 轻 | 培训、内部分享、活动、科普、团队介绍 | 中 / 低 |

用户没说受众、只给了一个中性题目（如「做一个关于 AI 的 PPT」）时，先在 Step2 的文字提问里问清受众与场合再打分；提问被跳过就按主题性质取「常规职场」。

选出的 3 套连同依据写进 STORY.md 开头一行（如「候选：经营分析 / 战略咨询 / 专题汇报；依据：面向管理层的方案评审，正式度常规职场偏上」），**只写文件，不对用户复述**。

#### 选定后的执行

- 读且只读所选套的 `DESIGN.preset.md`（路径取 `assets/templates/index.json` 该套的 `preset` 字段，相对技能根目录，实际在 `assets/templates/<slug>/` 下），以它为本项目 DESIGN.md 的主体（Step5 持久化的就是它），再按 STORY.md 补页面映射表（表式见 [design-principle.md](design-principle.md) §2）。
- 内容结构一律按 [content-contract.md](content-contract.md)（页型、信息下限、卡片纪律、硬闸门）；命中政务闸门时叠加 [government-contract.md](government-contract.md)，同一维度冲突取严者。
- 配色按 [templates/README.md](templates/README.md) §3 每次推导（用户点名的颜色优先）。
- **内容契约与预设冲突时**：母版分区、配图、色彩、字体、装饰以**预设**为准；页型、信息下限、硬闸门以**内容契约**为准。

### Step5：创建在线演示文稿并持久化设计契约
> **本步是硬约束，且两个动作不可拆分。**
>
> 1. **创建空的在线演示文稿**（`doc create`），拿到 `docid`。见 `pptx-api.md` §生成类接口（**不查 schema**，只传 `doc_type` + `doc_name`）。
>    ⚠️ 新建文档**自带一页空白首页**（索引 0），**本步立即删除**（`slide pages delete`，见 `pptx-api.md` §生成类接口与 [pptx-edit.md](pptx-edit.md) 索引）。之后生成页从 `page_index=0` 起依次填入。
> 2. **立即把设计契约持久化到该文档**——`design_md`（`DESIGN.md`）与 `story_md`（`STORY.md`）**必须同一次调用一起提交**，只传一个会失败。见 `pptx-api.md` §生成类接口。
>
> 🔴 **第 2 步不是可选增强，是写操作的前置门**：设计契约未写入时，后续所有插页、插图、改文字操作都会被服务端**直接拒绝**。跳过本步会导致 Step7 全量失败。
>
> 设计契约有效期 **24 小时**。因此 `DESIGN.md` / `STORY.md` / 每页源码**必须在本地保留副本**——既用于超时后重新写入，也用于页面改坏时整页重做（本链路**没有原生撤销**）。

### Step6：配图准备
> **当前环境没有生图工具，不提供 AI 配图**：不调用任何生图接口、不用图生图、不反复重试。本步只处理用户材料图——先按 `DESIGN.md` 页面映射表的「L1 来源」列清点材料图位（该列依据所选套预设 §4「图位」填写，只能填 `材料图` / `SVG` / `版式替代` / `—`），材料图要过 templates/README.md §5 的门槛，拿到 `url` 后把接口实际返回的宽高记入工作目录的 `images.json`。没有合格材料图时本步直接跳过，图位改用 `<SVG>` / 色块 / 版式留白承载（见 `component-image.md` §P1）。
>
> **对外不提配图**：没有生图能力是既定形态，不是故障。交付时不说「无法生成配图」，不把它说成服务问题，不建议用户手动加图、不列「可配某某照片」的清单（接口真的报错时按 Step7 的报错规则如实说明，不在这里编理由）。用户主动问起配图时，如实说明本技能当前只用用户提供的材料图，可以把照片发过来。
>
> 图片**统一经上传口进 PPT**，两个来源到达出口的路径不同。完整命令见 `pptx-api.md` §配图接口。
>
> | 图片来源 | 获取路径 |
> |---|---|
> | **材料图**（用户上传、用户提供的品牌/产品图） | `media_id` 直传（或本地文件传 `file_path`）→ **上传口** → `url` |
> | **材料内嵌图**（pptx / docx / xlsx 里的图） | `media download` 下载文档 → `doc_image_extractor.py` 抽出本地图 → 以 `file_path` 上传 → `url` |
> | **用户模板的底图 / 页眉页脚家具** | 不手工上传：建文档后跑一次 `build_page.py template --docid <docid>`，它逐张上传并写回外壳（create-from-template.md T4） |
>
> 🔴 **所有图片都必经 `wecom-cli smartpage images upload` 上传口**（上传需要 `docid`，故本步在 Step5 建文档之后）：会话图片的 `media_id` 不进 PPT，本地文件不进 PPT，任何公网图片直链不进 PPT。
>
> 拿到 `url` 后**同一条落法**：直接写进 JSX 里 `<Image>` 的 `src`，与文字、图表同页一次性插入。**Step6 要把每个图位的 URL 一次性备齐**（页号 → URL → 宽高），供 Step7 逐页取用。
>
> 🔴 **材料图一律原图直传、零重绘**——任何二次加工都会让数字 / 文字 / 细节走样。
>
> **配图前置**：用到的材料图必须在写该页内容前完成上传与核对，确认清晰、完整、符合上下文后方可使用。
>
> 建议在本步一次性清点全篇图位（依据 `DESIGN.md`），而非边写边想。

### Step7：逐页生成并插入（按大纲顺序）
> 动笔前的心智校准：每一页是一段 JSX 源码，但**它不是 React**——这是一套受限 DSL，由服务端编译成幻灯片。把它当 HTML + 内联 CSS 来写。禁止引入 React 生态任何概念（`import` / `export` / `module` / hooks / state / 函数组件定义），**禁止使用 `<View>` 组件**——容器一律用 `<Box>`；源码最后一个表达式必须是 `<Slide>`。
>
> 动笔前必读：
> - `STORY.md` - 当前PPT的叙事逻辑
> - `DESIGN.md` — 当前 PPT 的设计稿（画布、配色、字号、布局、元素、密度）
> - 相关组件规范 — 本页用到哪个组件，就读取 `component-*.md` 中对应文档
> - 🔴 **工作目录里的 `ref_*.slide`（`init` 复制进来的范例页，已换好色）——每页动笔前必须打开其中骨架最接近的一页，在它的结构上改内容**：保留它的分栏、卡片形状与间距、字号层级、序号与标志性处理，只把文字和数据换成本页的。不是「看一眼找灵感」，是照着它改。范例未覆盖的页型才按 `DESIGN.preset.md` §5 设计，色彩字体不越界。范例是唯一允许「借鉴」的页面源码，占位内容必须全部替换；不写注释
> - 本页照的是哪个 `ref_*`，写进 `DESIGN.md` 页面映射表的「骨架」列；写不出来说明没照范例，返工
>
> **外壳靠脚本拼装（防抖动，硬约束）**：开工时先按 README §3 跑 `palette` 生成 `colors.json`（用户点名默认配色时才跳过），再执行一次 `python3 "{baseDir}/scripts/build_page.py" init --set <slug> --map colors.json` 把外壳、范例页、预设复制并换色到工作目录（不要对技能目录跑 `cp`；脚本路径整段加双引号；手写命令时让当前目录就是工作目录、页面文件一律用裸文件名如 `00_shell.jsx`，由程序拼命令时改为显式传 `--out` / `--dir`，见 [templates/README.md](templates/README.md) §4）；每页只写 `NN_body.jsx` 与 `NN_vars.json`，写完后执行 `python3 "{baseDir}/scripts/build_page.py" buildall` 一次性拼页并做机检，`ALL OK` 才提交 `NN_page.jsx`。`{baseDir}` 表示当前 Skill 所在目录（`wecomcli-pptx`），执行时必须替换为实际绝对路径；脚本已经存在，直接运行，禁止先做脚本存在性检测。细则见 [templates/README.md](templates/README.md) §4。
>
> **动笔前禁读**：本项目目录之外的任何 PPT 项目源码。本页 JSX 的全部依据应来自 `DESIGN.md` + 本地 `00_shell*.jsx` + 所选套的范例源码 + `content-contract.md`（命中政务闸门时加 `government-contract.md`）+ `component-*.md`，不得"借鉴"历史项目的写法或视觉选择。
>
> 严禁仅靠记忆动笔。

约束如下：
- 充分结合 `STORY.md` 和 `DESIGN.md`，按照大纲顺序从第 1 页生成到第 N 页；
- **每页两个动作，逐页闭环**（不要写完全部页面再统一提交）：
  1. 本地 `write_to_file` 保存该页源码：内容页是 `NN_body.jsx` + `NN_vars.json`，由 `buildall` 拼成 `NN_page.jsx`；封面等非外壳页直接写 `NN_<名称>.jsx`。`DESIGN.md` 页面映射表的「源码文件」列填提交用的 `NN_page.jsx` / `NN_<名称>.jsx`（**这是"改坏了"唯一的回退依据，不可省**）；
  2. 提交该页 → `addjsx`（**单页异步命令**，N 页 = N 次调用）：**用 python 从第 1 步的文件读出源码**组装 payload（见 `pptx-api.md` §命令形态 的红线），**不要把刚写完的源码原文再贴一遍进命令**——那会让同一份内容在上下文里出现两次；图位 `src` 已写上传口 URL（Step6 备齐）。🔴 **`page_index` 必填**，传明确递增索引——第 N 页大纲对应 `page_index=N-1`（Step5 已删除空白首页，索引从 0 起排），**不得省略、不得传 `-1` 追加**。服务端编译成幻灯片，**无后置补图动作**。
- 逐页串行推进；**某页失败只重试该页**，不回滚已成功的页面；**渲染溢出、编译报错同样只整页重做该页**（改本地源码后用目标 `page_index` 替换提交），**禁止回到 Step5 重新创建文档**，一次生成任务只允许存在一份在线文档；修完该页必须继续生成剩余页面，不得停在中途等待；
